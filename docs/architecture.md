# architecture.md — как устроен RED SIGNAL

Что делает игра — в `product-logic.md`. Здесь — **как** она устроена и по каким правилам пишется код. Порядок работ — в `phases.md`, арт и звук — в `assets.md`. Этот файл и `AGENTS.md` в корне надо давать своему ИИ-ассистенту перед каждой задачей.

**Состояние.** Фундамент закончен и проверен (`foundation-status.md`): `npm run check` зелёный (98 тестов), онлайн и соло проходятся, деплой подготовлен. Идёт **v2** — сценарии, режиссёр, разведка, локализация эпицентра, RED SIGNAL, поломки (план — `phases.md`). Разделы, помеченные **v2**, описывают целевое устройство: до фазы 0 этих файлов и полей ещё нет.

Что **не** проверялось: реальные видеокарты и слабые ноутбуки (в проверке был программный рендер), Safari и Firefox, публичный хостинг с двух сетей.

## 1. Стек

Все версии **закреплены точно** и лежат в `package-lock.json`. Ставим только через `npm ci`.

### Решение: Phaser 3.90, а не Phaser 4

Последняя версия в npm — Phaser 4.2 (вышел в апреле 2026). Мы **намеренно** берём 3.90 — финальную версию третьей ветки:

- В Phaser 4 заменены как раз те части, на которых стоит наш вид: эффекты и маски стали «фильтрами», конвейеры рендера убраны, API текстур для рисования изменён. Приём «тёмный слой, из которого вырезается свет» в 3.90 проверен у нас запуском.
- ИИ-ассистенты знают API третьей версии намного лучше и будут путать версии.
- После хакатона перейти можно: есть официальное руководство по миграции.

**Правило:** `npm i phaser` поставит четвёрку и всё сломает. Версию не трогать. Если ассистент предлагает `filters`, `enableFilters`, `RenderNode` — это API четвёрки, отклонять.

### Чего в стеке нет и почему

- **Базы данных и аккаунтов** — комнаты живут в памяти сервера, этого достаточно.
- **Colyseus** — мощнее, но схемы состояния и декораторы дают лишние ошибки; для 4 игроков полный снимок 15 раз в секунду проще и надёжнее.
- **Сборки сервера** — сервер запускается через `tsx` прямо из исходников.
- **ESLint** — строгий TypeScript + Prettier + тесты закрывают нужное; меньше трения.
- **Новых зависимостей** — запрещены без общего решения (см. раздел 13).

## 2. Общая схема

```
┌──────────────────────────── браузер ────────────────────────────┐
│  React-экраны (lobby, design, console, report, HUD)             │
│      ▲ читают store (≤ 5 обновлений/с)                          │
│  Phaser FieldScene / canvas пульта                              │
│      ▲ читают snaps (каждый кадр, мимо React)                   │
│                    net/session.ts                               │
│                         │ Transport (join / send / onMessage)   │
│        ┌────────────────┴───────────────┐                       │
│  SocketTransport                  LocalTransport                │
└────────┼────────────────────────────────┼───────────────────────┘
         │ Socket.IO: 'join', 'msg'       │ тот же класс прямо в браузере
┌────────▼──────────┐              ┌──────▼────────┐
│ server/app.ts     │              │  GameRoom     │  ← соло и офлайн
│ комнаты, 15 Гц    │──► GameRoom ─┘  (shared)     │
└───────────────────┘      │
                           ▼
                 sim: конвейер систем (weather → power → comms → oxygen → …)
```

Главная идея: **вся игра — в `shared/`**, чистый TypeScript без сети и таймеров. Сервер — тонкая обёртка с сокетами. Клиент в соло-режиме запускает тот же класс внутри браузера. Отсюда:

- правила тестируются без сети и без браузера — быстро и детерминированно;
- соло-режим не требует отдельного кода и работает без сервера;
- если хостинг упадёт на защите, игра всё равно запустится в соло.

## 4. Девять принципов

1. **Движок в `shared/` чистый и детерминированный.** Одинаковые seed и входы → одинаковое состояние бит в бит. Это закреплено тестом.
2. **Сначала контракт.** Формы данных и сообщения (`types.ts`, `protocol.ts`) общие для всех. Они уже полные: большинство фич добавляется без их изменения.
3. **Сервер — главный.** Клиент шлёт намерения, сервер решает. Исключение одно: позицию своего астронавта клиент считает сам (для мгновенного отклика), сервер проверяет длину шага.
4. **Данные, а не код.** Модуль, место посадки, сложность — строка в `catalog.ts`. Число — в `balance.ts`. У каждого модуля в каталоге шесть свойств: цена, масса, мощность, отсеки, поток данных, группа; итог по каждому ресурсу считает `checkDesign()`.
5. **Рельеф не ходит по сети.** Сервер и клиент считают его из одних функций.
6. **React — только для редкого.** Всё, что меняется каждый кадр, рисуют Phaser или canvas, читая `snaps` напрямую.
7. **Движок не падает от входных данных.** Любое сообщение клиента проверяется по каждому полю.
8. **Все тексты — в `i18n/`**, на английском.
9. **`main` всегда играбелен.** Недоделанное недостижимо из интерфейса.

## 5. Контракт

Полные определения — в `shared/src/types.ts` и `shared/src/protocol.ts` (в них комментарии к каждому полю). Здесь — карта.

### 5.1. Два потока данных от сервера

| Сообщение | Когда | Что внутри |
|---|---|---|
| `{ t: 'state', state: RoomState }` | При любом изменении комнаты | Фаза, игроки, проект, результат проверки проекта, параметры миссии, отчёт |
| `{ t: 'snap', snap: EvaState }` | 15 раз в секунду во время вылазки | Время, астронавты, корабль, участки, станции, сейсмособытия, опасности, погода, спутник, эффекты, журнал |
| `{ t: 'error', code }` | В ответ на недопустимое действие | Код ошибки |

`EvaState` шлётся **целиком** каждый тик. Для четырёх игроков это 2–4 КБ; тест следит, чтобы было меньше 16 КБ. Дельты не нужны и запрещены: с ними больше ошибок, чем пользы.

### 5.2. Сообщения клиента (`ClientMsg`)

| Группа | Сообщения | Кто может |
|---|---|---|
| Лобби | `lobby:role`, `lobby:ready`, `lobby:start` | все / хост для start |
| Конструктор | `design:set`, `design:module`, `design:preset`, `design:launch` | все / хост для launch |
| Астронавт | `eva:move`, `eva:dig`, `eva:interact`, `eva:ping` | роли `eva`, `solo` |
| Оператор | `mc:waypoint`, `mc:clearWaypoint`, `mc:classify`, `mc:power`, `mc:ration`, `mc:dispense`, `mc:alert`, `mc:liftoff` | роли `mc`, `solo` |
| Отчёт | `report:again` | хост |
| Отладка | `debug` (`skip_phase`, `set_time`, `drain_o2`, …) | только если сервер запущен не в production |

Вход в комнату — отдельное событие `join` с ответом `JoinResult`: при успехе клиент получает `playerId`, `token` для переподключения и текущее состояние.

### 5.3. Скрытое состояние

`Sim.hidden` (расписание событий с правдой о типе, статистика, счётчики) **никогда не попадает в снимок**. Тип сейсмособытия появляется в снимке (`SeismicEvent.truth`) только после решения оператора или истечения времени.

### 5.4. Одноразовые эффекты

`EvaState.fx` — список событий вида `{ id, t, type, x?, y?, playerId?, n?, s? }`, которые живут в снимках 2 секунды. Клиент проигрывает каждый `id` один раз (запоминает последний обработанный). Так звук и вспышка не теряются и не повторяются.

`EvaState.log` — последние 20 записей журнала радио; тексты — ключами i18n. В v2 поле `from` бывает ещё `earth` и `tulpar` — голоса сюжета (PL 5.2).

## 6. Движок

### 6.1. GameRoom

```ts
const room = new GameRoom({ code, seed, emit, makeId?, allowDebug? });
room.join({ name, token? })      // → JoinResult
room.disconnect(playerId)
room.handle(playerId, msg)       // никогда не бросает исключений
room.tick(TICK_DT)               // один шаг 1/15 с; часы — снаружи
room.state                       // RoomState
```

- `emit(target, msg)` — единственный выход наружу; `target` — id игрока или `ALL`.
- Часы принадлежат вызывающему: сервер и LocalTransport сами зовут `tick`. Тесты «проматывают» 10 минут миссии за миллисекунды.
- Фазы и переходы — раздел 5.4 `product-logic.md`. Запуск: `deriveParams(design, seed + attempt, scenario)` (v2: у тренировки seed фиксированный) → `createSim(params, idАстронавтов)`.

### 6.2. Симуляция

`Sim = { pub: EvaState, hidden: SimHidden, params: MissionParams, salt }`.

Один шаг — `stepSim(sim, dt)`: время +dt, затем системы по порядку из `sim/step.ts`:

```
v1: weather → power → comms → oxygen → digging → lander → seismic → hazards → endCheck

v2: director → weather → flare → power → comms → devils → oxygen → digging → discovery
      → faults → lander → seismic → signal → hazards → objectives → endCheck
```

Порядок важен и меняется только отдельным согласованным изменением. Почему так в v2: режиссёр первым ставит события этого шага; вспышка до энергии и кислорода (доза зависит от того, кто снаружи); энергия читает поломки и пыль; вихри до кислорода (расход внутри вихря); открытие после копания; поломки до корабля (MOXIE); сигнал после сейсмики (сужение зоны по решённым импульсам); задачи — после всех, перед проверкой конца.

**Система** — функция `(sim, dt) => void` в своём файле, которая меняет `sim.pub` и `sim.hidden`. Чтобы добавить поведение, правят файл системы; в `step.ts` не лезут.

**Сообщения клиента** применяются в `sim/input.ts`: `handleSimMsg(sim, playerId, canEva, canMc, msg)`.

### 6.3. Правила детерминизма

- В `shared/src/sim` запрещены `Math.random()`, `Date.now()`, `performance.now()`. Случайность — только `createRng(seed)`; время — только `sim.pub.t`.
- Генератор для каждой подсистемы создаётся из seed с собственной «солью», чтобы изменение одной системы не сдвигало случайность другой. Занятые соли (новую — дописать сюда):

| Соль | Система | Соль | Система |
|---|---|---|---|
| `0x51735` | участки (`generateSites`) | `0xd17` | v2: режиссёр |
| `0x5e15` | расписание free (`buildSchedule`) | `0x516` | v2: источник RED SIGNAL |
| `0x570a` | буря | `0xa40` | v2: аномалии |
| `hashString(eventId)` | оценка эпицентра | `0xde7` | v2: пылевые вихри |
| `^ hash(eventId) ^ stationIdx` | v2: кольца дальности | `0xfa17` | v2: поломки |
- Не перебирать `Map`/`Set`/ключи объектов там, где порядок влияет на результат; использовать массивы.
- Тест `is deterministic for the same seed and inputs` должен оставаться зелёным.

### 6.4. Проверка входных данных

- Числа: `typeof v === 'number' && Number.isFinite(v)`.
- Координаты: `clampToWorld`.
- Идентификаторы из сообщений ищутся в таблицах через `hasOwnProperty` (защита от `__proto__`).
- Строки обрезаются по длине.
- Роль проверяется для каждой группы сообщений.
- Тест `never throws on garbage input` пополняется при добавлении каждого нового сообщения.

### 6.5. Сценарии, биты и режиссёр **v2**

- **Сценарий — данные**, не код: `shared/src/scenarios/<id>.ts` экспортирует объект `ScenarioDef` (длительность, закат, фиксированный seed и место, развёртываемые станции, известные кольца участков, `scienceFull`, пресет Quick start, биты, акты режиссёра, построитель задач). `SCENARIOS` в `scenarios/index.ts` собирает их.
- **Путь сценария в движок:** хост шлёт `lobby:scenario` → `RoomState.scenario` → `deriveParams(design, seed, scenario)` кладёт в `MissionParams` всё, что нужно системам → `createSim` по `params.scenario` достаёт `SCENARIOS[...]` для битов, актов и задач. Системы читают только `params` и `sim`, а не глобальный выбор.
- **Биты** — `{ at, action }`: радиосообщение, событие в точке или «рядом с экипажем», вспышка, буря, поломка, смена акта, «окно закрывается». `directorSystem` выполняет каждый бит один раз, когда `t ≥ at`, и отмечает это в `hidden.director`.
- **Режиссёр** работает только там, где у сценария есть акты. На каждом шаге: если `t ≥ nextAt` и напряжение низкое — выбрать событие из пула текущего акта генератором режиссёра, поставить его через «ручку» нужной системы (`hidden.schedule.push` для сейсмики, `spawnDevil`, `spawnFault`, `scheduleFlare`) и назначить `nextAt`. Режиссёр не знает, как устроены системы, — только их ручки.
- **Напряжение** считается из публичного состояния (кислород, лежащие), поэтому одинаковые входы дают одинаковую миссию: детерминизм сохраняется.

### 6.6. Скрытое и публичное в v2 **v2**

Правило 5.3 расширяется: всё, что игрок должен **вычислить или найти**, живёт в `Sim.hidden`.

| Скрыто (`hidden`) | Публично (`pub`) |
|---|---|
| Скрытые участки с точными координатами | `anomalies`: сдвинутый центр и радиус; вид и богатство — только с георадаром |
| Источник RED SIGNAL | `signal.zone` — круг, в котором он точно есть; `signal.located/found/retrieved` |
| Полный план вспышки | `flare` — только с момента предупреждения |
| Кризис третьего акта, план режиссёра | ничего, пока событие не произошло |
| Настоящий эпицентр | `distEst`, `bearingEst` с ошибкой; `pick` оператора; зона предупреждения |
| Хронология для отчёта | попадает в `MissionReport.timeline` только в отчёте |

Сканер шлема (`Astronaut.scan`) — единственная намеренная «утечка»: расстояние и направление до ближайшего скрытого участка в радиусе сканера. Это механика, а не дыра.

## 7. Сеть

- **События Socket.IO:** `join` (с подтверждением) и `msg` в обе стороны. Имена — константы `EV_JOIN`, `EV_MSG`.
- **Тик:** один цикл на все комнаты, шаг строго 1/15 с, накопитель времени компенсирует неточность таймера; после подвисания догоняем не больше 5 шагов.
- **Движение своего астронавта:** клиент двигает его сразу и 15 раз в секунду шлёт `eva:move` с позицией. Сервер ограничивает шаг: скорость × прошедшее время × 1,6. Если клиент разошёлся с сервером больше чем на 24 px — прыгает к серверной позиции.
- **Чужие астронавты:** клиент сглаживает их движение между снимками (в скелете — простое сглаживание; задача B1 заменяет на интерполяцию с отставанием 100 мс).
- **Переподключение:** клиент хранит токен; после обрыва Socket.IO переподключается сам, клиент заново шлёт `join` с токеном и получает свой слот. В лобби отключившийся игрок удаляется, в игре — помечается `connected: false`.
- **Комнаты:** код из 4 букв без похожих символов; до 200 комнат; пустая комната удаляется через 5 минут.
- **LocalTransport:** тот же `GameRoom` в браузере; сообщения копируются через `structuredClone`, чтобы интерфейс не мог случайно изменить состояние движка — как при настоящей сети.

Целевая структура сцены (скелет содержит первые версии, задачи B1–B6 развивают):

| Модуль | Отвечает за |
|---|---|

| HUD | React поверх canvas (`screens/eva/`) |

**Алгоритм текстуры мира** (он дал утверждённую картинку на концептах):

1. Один раз заполнить массив уровней `Uint8Array(1536×1536)` через `levelAt(x, y, salt)`. Дальше работать только с массивом — без тригонометрии в циклах.
2. Базовый цвет пикселя — по уровню (5 цветов из `product-logic.md`, раздел 12).
3. Зерно: на блок 2×2 пикселя псевдослучайно ±14 к яркости (хэш от координат, а не `Math.random`).
4. Рябь дюн на нижнем уровне; сетка трещин на верхнем.
5. Тени: если пиксель на `k` шагов вверх-влево выше уровнем — затемнить (`k` от 1 до 6: чем ближе, тем темнее, с лёгким уходом в синий).
6. Кромка: пиксель выше своего соседа справа-снизу → тёмная линия. Пиксель выше соседа слева-сверху → светлая линия.
7. Записать в canvas-текстуру (`textures.createCanvas`) и показать одним изображением.

Бюджет: не дольше 400 мс; выполнять под заставкой отсчёта. Контурную карту для пульта считает сам пульт: `levelAt` по сетке 4 px, один раз в отдельный canvas.

**Свет** (проверено запуском): экранная `RenderTexture` поверх мира; каждый кадр `clear()`, `fill(ночной цвет, 1 − освещённость)`, затем для каждого источника `erase(текстура света, x, y)`. Текстуры света создаются один раз: радиальный спад в четыре ступени с матрицей Байера 4×4 в альфа-канале — дизеринг получается бесплатно. Освещённость — `snap.weather.light`.

### 8.4. Пульт оператора

Раскладка — React и CSS; карта и графики — canvas с собственным циклом кадра, читающим `snaps`.

**Сейсмограф.** Для сигнала станции `s` и времени от начала `τ = t − t0 − s.delayS`:

```
env(τ)  = 0 при τ < 0, иначе  s.amp · min(1, τ / s.riseS) · exp(−max(0, τ − s.riseS) / s.decayS)
wave(τ) = env(τ) · sin(2π · s.freqHz · τ + φ) · (0.7 + 0.3 · sin(2π · 0.37 · s.freqHz · τ))
y(τ)    = wave(τ) + s.noise · n(τ)
```

`n(τ)` — псевдошум от хэша `(id события, номер станции, floor(τ·30))`: все клиенты видят одинаковый график. `φ` — тоже от хэша. График давления: `−s.pressureDip · exp(−((τ − 1.5) / 1.2)²)`. Окно — последние 20 секунд, лента едет влево.

**Вид старого монитора** — только CSS, без шейдеров: полупрозрачный слой с `repeating-linear-gradient` (строки развёртки), `radial-gradient` (затемнение краёв), `text-shadow` (свечение). Никаких `filter: blur()` на больших областях.

## 9. Звук

- Один модуль `client/src/audio/index.ts` (объект `audio`) на Howler: `unlock()`, `sfx(name, opts?)`, `loop(name)`, `stop(name)`, `setTension(0..1)`, `setVolume(kind, v)`, `mute(bool)`.
- **Разблокировка:** браузеры не дают играть звук до первого клика или клавиши. `unlock()` вызывается из обработчика кнопки в лобби.
- **Реестр звуков:** имена — в `audio/soundManifest.ts` (только данные), поиск файлов по имени — в `audio/sounds.ts`. Полный список имён и правила для звукорежиссёра — `assets.md`, раздел 5. Отсутствующий файл — не ошибка: играет запасной тон. Неизвестное имя или не та папка — ошибка `npm test` (`tools/assets.test.ts`).
- **Картинки:** манифест `game/assetManifest.ts` (ключ, размер кадра, число кадров, `field` или `ui`). Phaser грузит только `field`; экраны React берут `ui`. Размеры проверяет тот же `tools/assets.test.ts`.
- **Музыка слоями:** три слоя стартуют одновременно и зациклены; `setTension` плавно (1,5 с) меняет их громкость.
- **Форматы:** в реестре указываются оба файла, `['x.ogg', 'x.mp3']`; Howler возьмёт первый поддерживаемый. Для бесшовных циклов нужен ogg.
- **Память:** зацикленная музыка декодируется целиком. Слой 85 секунд стерео — около 30 МБ в памяти. Три слоя — 90 МБ: допустимо, но лучше моно или цикл покороче.
- **Связь с игрой:** `FxBus` получает `snap.fx` и вызывает `audio.sfx(...)`; пульт и HUD вызывают звуки интерфейса напрямую.

## 10. Производительность

Цель: **60 кадров в секунду на ноутбуке со встроенной графикой**, отзывчивость сети — в пределах одного тика.

### 10.1. Бюджеты

| Тик сервера на комнату | < 2 мс | Тест |
| Размер снимка | обычно 2–4 КБ, предел 16 КБ | Тест |

| Текстуры | Одна текстура мира 1536×1536; предел размера любой текстуры 2048 | — |

### 10.2. Правила

- Внутреннее разрешение 480×270 — это уже главная оптимизация: видеокарта рисует 130 тысяч пикселей вместо двух миллионов.
- Мир — одно изображение, а не тысячи тайлов.
- В циклах кадра не создавать объекты и массивы: заводить один раз и переиспользовать.
- Не перерисовывать `Graphics` каждый кадр ради многих фигур — использовать спрайты.
- Canvas пульта: рисовать в целых координатах; статичные слои (контуры рельефа) — один раз в отдельный canvas и копировать.
- CSS-эффекты — только `opacity` и `transform` для анимаций; без `box-shadow` и `filter` на больших областях.
- Музыка загружается после лобби, не блокируя первый экран.
- Вкладка в фоне: браузер останавливает кадры. Сервер продолжает игру; при возврате клиент берёт позицию с сервера.

С `?debug=1` в углу: кадры в секунду, время скрипта на кадр, пинг, размер последнего снимка, тик сервера, число спрайтов.

npm run dev            # сервер :3001 + клиент :5173 с прокси сокетов
npm run check          # всё, что проверяет CI

### 12.2. Хостинг

Нужен любой хост, который держит процесс Node и WebSocket. Пример — Render (бесплатный веб-сервис):

- Build Command: `npm ci --include=dev && npm run build` (флаг обязателен: в production-окружении без него не поставятся Vite и TypeScript — проверено).
- Start Command: `npm start`.
- Версия Node — 22: в репозитории есть `.nvmrc`; если хост его не читает, задать версию в настройках. Порт берётся из `PORT` автоматически.
- Health Check Path: `/healthz`.

**Особенность бесплатного тарифа:** сервис засыпает после 15 минут без входящих запросов и просыпается около минуты. Перед защитой открыть ссылку за 5 минут и держать вкладку с игрой открытой.

### 12.3. Запасной вариант без сервера

Папку `client/dist` можно выложить на любой статический хостинг (GitHub Pages, itch.io): пути в сборке относительные. Онлайн-комнаты там работать не будут, **соло-режим — будет**. Эту ссылку стоит указать второй в описании проекта.

## 13. Работа в git без конфликтов

### 13.1. Правила

1. **Ветка от `main`, живёт не дольше двух часов.** Имя: `a/locate`, `b/discovery` (буква — разработчик из `phases.md`), `art/astronaut` для ассетов.
2. **Одна задача — один небольшой PR** (ориентир: до 300 строк). Слияние — squash. После слияния ветка удаляется.
3. Перед пушем: `git pull --rebase origin main`, затем `npm run check`.
4. **Трогаем только свои папки** (таблица в разделе 3).
5. CI обязателен для слияния; ревью — по желанию, чтобы не ждать друг друга.
6. Никаких массовых переформатирований и переименований чужих файлов.
7. Формат коммита — в `AGENTS.md`.

### 13.2. Горячие файлы 🔒

`shared/src/types.ts`, `shared/src/protocol.ts`, `shared/src/sim/step.ts`, `shared/src/index.ts`, `client/src/App.tsx`, все `package.json`, `package-lock.json`.

Порядок изменения:

1. Написать в чат команды: «🔒 меняю types.ts: добавляю поле X».
2. Сделать PR **только** с этим изменением (плюс минимальная правка, чтобы всё собиралось).
3. Слить в течение 10 минут. Остальные сразу делают `git pull --rebase`.

В v2 горячие файлы `shared/` меняет только **A** (хранитель контракта): все поля сразу — в контрактном PR фазы 0, позже — «мини-контрактом». `App.tsx` меняет только **B**.

`balance.ts` не горячий, но общий: каждый правит **только свои блоки**, подписанные `// owner: A` или `// owner: B` (блоки заводит контрактный PR, поэтому правки идут в разные места файла и не конфликтуют). `catalog.ts` правит B. Данные сценариев (`shared/src/scenarios/`) правит A.

### 13.3. Почему конфликтов будет мало

- **Зависимости уже все установлены.** `package.json` и lock-файл больше никто не трогает.
- **Каждая система симуляции, каждый экран, каждый модуль сцены — отдельный файл** со своим владельцем.
- **Тексты разбиты по экранам** (`i18n/en/lobby.ts`, `i18n/en/design.ts`, …) и собираются автоматически по маске файлов; общего файла-списка нет. Так же собираются страницы площадки `?dev=`.
- **Ассеты — только новые файлы** с заранее заданными именами; один файл — один автор. Бинарные файлы не сливаются, поэтому два человека не правят один PNG. Имена и размеры проверяет `npm test`, поэтому ассеты идут через PR (`art/...`) с зелёным CI, а не прямым пушем в `main`.
- **Системы v2 созданы заглушками в фазе 0** с финальными сигнатурами «ручек»: каждый наполняет свой файл, общие файлы почти не трогаются.
- **Окончания строк** принудительно LF (`.gitattributes`), форматирование единое (Prettier) — нет «пустых» различий между Windows и Mac.
- **Контракт уже содержит поля для всех фич из `product-logic.md`** — менять его почти не придётся.

### 13.4. Стабильные точки

После каждого успешного смоук-теста на `main` ставится тег: `git tag demo-stable-N && git push --tags`. Если перед защитой что-то сломалось — выкатываем последний тег.

Недоделанная фича не должна быть достижима из интерфейса: кнопка скрыта или действие ничего не делает.

## 14. Соответствие правилам хакатона

- **Раскрытие ИИ.** Раздел «Use of AI» в `README.md` заполняется честно: какие инструменты и для чего (код, арт). То же — в поле формы сдачи.
- **ИИ-изображения разрешены решением команды**, но только с видимой пометкой «AI-generated». В игре это постоянная надпись в углу: константа `SHOW_AI_ART_NOTICE` в `client/src/ui/aiNotice.ts`, по умолчанию включена. Выключать только если весь арт сделан руками. На слайдах и в видео пометка тоже нужна.
- **Никаких логотипов NASA, флагов и эмблем миссий** — ни в игре, ни в слайдах, ни в сгенерированных картинках.
- **Всё чужое — в `docs/REFERENCES.md`:** данные и звуки NASA, шрифты, библиотеки, ассеты, с лицензиями.
- **Репозиторий публичный**, ссылка открывается без входа.
- **Английский** — в интерфейсе, коде, `README.md` и форме сдачи.
